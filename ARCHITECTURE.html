FileForge — internal reference

How FileForge actually works

A plain-English map of the two things happening behind the site: how the 63 tool pages get built and deployed, and what happens on a visitor's screen between landing on the page and downloading their file — without a server ever seeing it.

01 The build & hosting pipeline

FileForge has no backend, no database, and no API server. Everything the browser ever receives is a plain HTML/CSS/JS file that was generated before anyone visits — the diagram splits at the point where that stops being true.

Build time — runs once, on your machine, before you deploy Every visit — runs fresh, inside the visitor's browser
  • Page generator
    scripts/generate-seo-pages.mjs reads the tool list once and writes out a dedicated HTML file per tool (63 of them), plus sitemap.xml, robots.txt, and the JSON-LD structured data each page carries for search engines.
  • Vite build
    Every .html file in the project root is auto-discovered as its own build entry. A small custom plugin (htmlPartials) stitches the shared header and footer into each one at build time, so there's one source of truth for nav and footer instead of 63 copies.
  • Cloudflare Workers
    The build's output folder is deployed as static assets — no server-side code runs after deploy. Cloudflare treats the extensionless URL as canonical and redirects .html links to it.
  • In the browser
    The page you shipped is just HTML/CSS/JS, so once it's downloaded, the file-processing libraries (PDF, image, Excel, OCR — whichever the tool needs) run using the visitor's own CPU. That's the entire "no upload" promise, made structural rather than just promised in the copy.

02 What a visitor actually does

The same "nothing leaves the browser" shape holds from the visitor's side, too — this is the path from first landing to walking away with a finished file.

Why the split matters

Because processing happens in zone two, FileForge can run without user accounts, storage costs, or a privacy policy about file retention — there's nothing retained to write a policy about. The build/hosting side (zone one) only ever handles page markup, never a visitor's actual file.
